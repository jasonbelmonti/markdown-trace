# Document graph proving corpus

This is the EP-ACT-2 source and interpretation corpus for the [interface packet](../../../markdown-trace-document-graph-interfaces.md). The [manifest](manifest.json) maps all 55 language cases and 24 API scenarios to exact Markdown bytes and independently authored annotations. Sources preserve trailing-newline differences deliberately; CASE-13 uses CRLF and an emoji. CASE-9C maps symbolic A/B to WP-1/REQ-1. CASE-10 includes both source versions. Shared inputs reference one annotation instead of duplicating it.

These are design oracles, not results from an implemented API. EP-ACT-3 still owns the generalized acceptance checker and complete validation/query/context result DTOs. The existing mixed-layout and ambiguous-context ledgers remain useful consumer examples. This corpus does not select the authoring syntax, close the entire parent task, or establish real-spec context/scale fitness.

## Reading annotations

Read the packet first, then a source file and its `.expected.json`. Each language record uses `markdown-trace.design-annotation.v1`; scenario-only records use `markdown-trace.design-scenario.v1` and resolve `annotationRef` relative to this directory. These names identify local design formats, not proposed public schemas. API scenario entries use the example profile unless an operation explicitly changes it. Language records describe lexical/ownership integrity using REQ=requirement, WP=work and VAL=validation; they do not assert the example profile's work/cardinality policy.

- Occurrences are exhaustive and ordered by source position. `O1`/`R1`/`F1` are local aliases. They are not runtime identifiers, and aliases from different source annotations must not be joined. Marker ranges include braces; identifier-only inline-code ranges include backticks and padding. `sourceText` is the exact slice. All offsets/columns count UTF-16 code units; lines/columns start at one and ends are exclusive.
- A relationship's `owners` contains declaration occurrence aliases: one means owned, none means unowned, multiple means ambiguous even if the labels match. Fragment `owners` uses the same convention. Definition occurrences remain distinct from the owner of their containing fragment. `identifiers` preserves missing and duplicate declaration states.
- Fragments give contiguous context ranges, ownership and required heading/header support. They preserve original list/quote indentation. They exclude final line terminators; internal terminators remain intact. Whitespace between blocks is not an independent context fragment. Splitting a fragment differently without changing source ownership or necessary support is a representation choice to reconcile in EP-ACT-3, not a license to include descendant-owned text. Mixed-layout fragment aliases here follow source order; the older ledger's F10 table support is F6 here, its F6 table row is F7, and F7–F9 are F8–F10 here.
- `exclusions` identify source intentionally contributing no occurrences; ordinary surrounding prose/punctuation is not exhaustively listed. Malformed groups are instead covered by `languageDiagnostics`, with the packet's specified code, severity, exact range and owner aliases. Their inner tokens never also appear as references or literal exclusions.
- `integrityObservations` record the expected missing/duplicate/unknown-kind and unowned/ambiguous-reference conditions. Their occurrence/declaration aliases locate source evidence. These semantic condition names are not invented public diagnostic codes or full validation reports. Missing targets alone leave coverage complete; malformed/unowned/ambiguous references make it partial. Ambiguous fragments without references do not themselves create analysis diagnostics.
- `operationExpectations` records each API scenario's semantic outcome and concrete input/budget variants. Any referenced fragments/relationships belong to its resolved annotation. It does not claim a live handle can be constructed from these JSON objects. Failed admission scenarios reference a source oracle but return no successful analysis.

## Independence and verification

Semantic choices were authored from the packet and raw fixtures before any Trace extractor exists. Temporary authoring helpers located explicitly selected anchors, converted coordinates and serialized redundant joins over manually enumerated facts; they did not recognize tokens, classify Markdown or infer owners. Two independent reviewers first interpret the full source inventory without opening these expectations, freeze their reports, then compare every case with the annotations. The gate's exact inputs, reports, comparison and resolution evidence live under `.codefactory/execution-plans/document-graph-contract-closeout/evidence/gate-1/` and `evidence/gate-1.json`.

The focused materialization check is `node .codefactory/execution-plans/document-graph-contract-closeout/evidence/verify-materialization.mjs`. It verifies source identities, exact slices and coordinates, alias joins, range containment and manifest membership. It does not infer semantic facts, run a proposed API, or replace EP-ACT-3's generalized result checker. Run the existing design declaration, ledger and parser checks from the companion README as supporting evidence.
