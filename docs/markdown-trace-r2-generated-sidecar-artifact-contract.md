## 1. Purpose

Generated sidecar artifacts let link-backed Markdown produce checked registry evidence without making generated output the only supported registry source. This contract defines the artifact path, serialized bytes, metadata, review policy, and follow-up validation expectations for the first R2 writer and check-mode tasks.

This contract does not approve replacing hand-authored YAML sidecars. During the transition, generated sidecars supplement the existing YAML sidecar path and preserve the current R0 compatibility boundary.

## 2. Artifact Path and Naming

A generated registry sidecar for a Markdown source document must live under a Markdown Trace sidecar directory adjacent to that source document:

```text
<source-dir>/.markdown-trace/generated/<source-stem><profile-segment>.entity-registry.yaml
```

Path terms:

| Term | Rule | Example |
| --- | --- | --- |
| `source-dir` | Directory containing the source Markdown document, expressed as a repository-relative path when recorded in metadata. | `fixtures/r1-link-backed-entity-syntax` |
| `source-stem` | Source Markdown basename without its final `.md` suffix. The generator must fail if the source path does not end in `.md`. | `minimal-link-backed-execution-spec` |
| `profile-segment` | Empty when no type profile is active. When a type profile is active, append `--profile-<profile-stem>-<profile-path-hash>`. | `--profile-minimal-type-profile-378211c9` |
| `profile-stem` | Profile basename without final `.yaml` or `.yml`, normalized to lowercase ASCII and replacing characters outside `[a-z0-9]+` with `-`. | `minimal-type-profile` |
| `profile-path-hash` | First 8 lowercase hexadecimal characters of SHA-256 over the repository-relative profile path using `/` separators. | `378211c9` |

Examples:

```text
fixtures/r1-link-backed-entity-syntax/.markdown-trace/generated/minimal-link-backed-execution-spec--profile-minimal-type-profile-378211c9.entity-registry.yaml
fixtures/r1-link-backed-entity-syntax/.markdown-trace/generated/codefactory-link-backed-spec--profile-codefactory-type-profile-1d87b2e3.entity-registry.yaml
fixtures/r0-document-local-registry/.markdown-trace/generated/execution-spec.entity-registry.yaml
```

The generated path must be deterministic from the repository-relative source path and active profile path. A writer must create only the `.markdown-trace/generated/` directory required for the selected source document. A check-mode command must not rewrite this file unless the operator explicitly chooses write mode.

## 3. Artifact Schema

The generated sidecar must remain loadable as a Markdown Trace registry by preserving the existing registry fields at the YAML document root:

```yaml
# Generated by markdown-trace; do not edit by hand.
registryVersion: markdown-trace.derived-registry.v0
document:
  id: markdown-trace.r1.fixture.minimal-link-backed
  title: Minimal R1 Link-Backed Fixture
  path: fixtures/r1-link-backed-entity-syntax/minimal-link-backed-execution-spec.md
  fixtureFamily: r1-link-backed-entity-syntax
  sourceDocs:
    - docs/markdown-trace-r1-link-backed-entity-syntax.md
generated:
  artifactVersion: markdown-trace.generated-sidecar.v0
  artifactKind: registry
  reviewMarker: generated-by-markdown-trace
  humanEditable: false
  source:
    documentPath: fixtures/r1-link-backed-entity-syntax/minimal-link-backed-execution-spec.md
    documentSha256: "<sha256>"
  typeProfile:
    path: fixtures/r1-link-backed-entity-syntax/minimal-type-profile.yaml
    pathSha256: "<sha256-of-repository-relative-profile-path>"
    contentSha256: "<sha256>"
    profileVersion: markdown-trace.type-profile.v1
  generator:
    packageName: markdown-trace
    packageVersion: 0.1.0
    command: markdown-trace derive-sidecar --document fixtures/r1-link-backed-entity-syntax/minimal-link-backed-execution-spec.md --type-profile fixtures/r1-link-backed-entity-syntax/minimal-type-profile.yaml
    serialization: yaml-lf-final-newline-v0
entities: []
edges: []
externalRefs: []
```

The `registryVersion`, `document`, `entities`, `edges`, and `externalRefs` fields must use the existing serialized registry shape. The `generated` field is additive metadata for generated artifacts. Current registry loading may ignore this field, but generated artifacts must include it.

When no type profile is active, `generated.typeProfile` must be omitted. When a type profile is active, `generated.typeProfile.path`, `generated.typeProfile.pathSha256`, `generated.typeProfile.contentSha256`, and `generated.typeProfile.profileVersion` are required.

## 4. Required Metadata

Generated artifacts must include deterministic metadata only. Metadata must not include timestamps, hostnames, absolute local paths, temporary directories, process IDs, or user-specific paths.

| Metadata field | Required | Rule |
| --- | --- | --- |
| `generated.artifactVersion` | yes | Must be `markdown-trace.generated-sidecar.v0` until a later migration contract changes it. |
| `generated.artifactKind` | yes | Must be `registry` for this sidecar contract. |
| `generated.reviewMarker` | yes | Must be `generated-by-markdown-trace`. |
| `generated.humanEditable` | yes | Must be `false`; reviewers should treat manual edits as drift unless a later task approves override policy. |
| `generated.source.documentPath` | yes | Repository-relative source Markdown path with `/` separators. |
| `generated.source.documentSha256` | yes | SHA-256 over the exact UTF-8 source Markdown bytes used for generation. |
| `generated.typeProfile.*` | when profile active | Records repository-relative profile path, path hash, content hash, and profile version. |
| `generated.generator.packageName` | yes | Must identify the generator package. |
| `generated.generator.packageVersion` | yes | Must identify the generator version or local package version used for review. |
| `generated.generator.command` | yes | Must record the reproducible command, using repository-relative paths and no shell-specific absolute paths. |
| `generated.generator.serialization` | yes | Must name the serialization contract, initially `yaml-lf-final-newline-v0`. |

The first line comment must be exactly:

```yaml
# Generated by markdown-trace; do not edit by hand.
```

The comment is a review marker, not parser data. The `generated.reviewMarker` field is the machine-checkable marker.

## 5. Deterministic Serialization

Generated sidecar bytes must be repeatable for identical source document bytes, type profile bytes, generator version, and command inputs.

Serialization rules:

- Emit one YAML document encoded as UTF-8.
- Use LF line endings and exactly one final newline.
- Do not emit timestamps, anchors, aliases, explicit document markers, trailing whitespace, or absolute local paths.
- Preserve this top-level key order: `registryVersion`, `document`, `generated`, `entities`, `edges`, `externalRefs`.
- Preserve the existing registry field names and edge serialization: edges use `from`, `relationship`, and `to`.
- Emit `document.sourceDocs`, `entities`, and `externalRefs` in the deterministic order returned by the derivation source or explicit input.
- Emit each entity's `expectedReferences.labels` in ascending lexical order.
- Emit each entity's `expectedReferences.ranges` in first-observed source order, with each range's `expandsTo` in registered label order.
- Emit `edges` in ascending lexical order by `from`, then `to`, then `relationship`.
- Use plain scalars for simple strings unless YAML quoting is required to preserve the exact value.

A future generator test must be able to run generation twice for the same source and profile and compare the emitted bytes exactly. A future check mode must compare regenerated bytes to the checked artifact and fail on any difference without rewriting the artifact.

## 6. YAML Sidecar Coexistence

Generated sidecars supplement existing YAML sidecars during R2 transition.

Coexistence rules:

- Existing hand-authored YAML sidecars, including `fixtures/r0-document-local-registry/entity-registry.yaml`, remain valid registry inputs.
- Generated artifacts must not replace `entity-registry.yaml` or change the `validate --registry` compatibility path in this task.
- When a YAML sidecar and generated sidecar both exist for the same source, reviewers may compare them as transition evidence, but the generated artifact is not replacement authority by itself.
- A mismatch between YAML and generated output is evidence for the later transition task unless the current writer/check task explicitly defines a blocking drift policy.
- A generated artifact may be passed to existing registry loading or validation code only because it preserves the root registry fields; that compatibility does not make the generated artifact the sole source of truth.

YAML replacement requires a later migration contract that defines review policy, drift policy, compatibility gates, and rollback criteria.

## 7. Review Policy

Reviewers should evaluate generated sidecar changes as checked artifacts:

| Review item | Approval impact | Evidence |
| --- | --- | --- |
| Artifact path matches this contract | blocking | Path is under the source document's `.markdown-trace/generated/` directory and includes the profile segment when a profile is active. |
| Root registry fields remain loadable | blocking | Existing registry loader can parse the artifact, or focused tests prove equivalent compatibility. |
| Metadata is complete and deterministic | blocking | Required `generated` fields exist and contain repository-relative paths and hashes. |
| Repeated generation is byte-stable | blocking for writer/check tasks | Two generation runs produce identical bytes. |
| YAML sidecar replacement is not implied | blocking | Diff preserves the existing YAML compatibility boundary. |
| Manual edits to generated output | blocking unless justified by a later policy | Review marker says generated output is not human-editable. |

For BEL-1217 itself, reviewers should block on ambiguous contract language or missing required clauses, not on the absence of writer/check implementation.

## 8. Follow-up Validation Evidence

Later R2 tasks should use this contract as their evidence target:

| Follow-up task | Required evidence |
| --- | --- |
| Minimal generated sidecar writer | Generate the minimal R1 fixture sidecar at the contract path; prove the artifact includes required metadata; prove the root registry fields load; prove repeated generation is byte-identical. |
| Drift check mode | Modify a checked generated artifact in a controlled test; prove check mode fails with a deterministic diff or drift diagnostic and does not rewrite bytes. |
| CODEFACTORY coverage | Generate the CODEFACTORY fixture sidecar using `fixtures/r1-link-backed-entity-syntax/codefactory-type-profile.yaml`; prove domain-specific entity types and profile metadata are preserved without Markdown Trace core taxonomy changes. |
| Transition evidence | Run existing R0 YAML validation and R1 generated-sidecar checks; record whether generated artifacts supplement or diverge from YAML controls; keep replacement criteria out of scope until a migration task approves them. |

## 9. Compatibility Statement

This contract starts from the R1 recommendation to generate checked sidecar artifacts while supplementing the existing YAML sidecar path. It preserves current registry semantics, keeps profile-backed `ctx://trace` behavior bounded to local files, and leaves writer behavior, drift policy, CODEFACTORY expansion, transition evidence, and YAML replacement for later reviewable tasks.
